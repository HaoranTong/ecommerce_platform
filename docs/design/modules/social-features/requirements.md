## 1. 业务背景

### 1.1 业务目标

- 支撑营销域“社交购物”能力，完善分享、邀请、奖励全链路（参考 `docs/requirements/functional.md §13`）
- 提供可追踪、可审计的裂变数据闭环，保障运营可度量与合规
- 通过标准化模块减少各页面重复实现分享逻辑，提高上线效率

### 1.2 核心业务场景

1. **商品分享裂变**：用户在商品详情页生成专属分享链接，好友点击后下单，邀请人获得积分奖励
2. **活动推荐有礼**：运营配置活动页分享任务，完成首单的被邀请人领取优惠券
3. **社群推广数据统计**：运营查看渠道和分享转化数据，优化渠道投放

### 1.3 成功指标（MVP）

- 分享链接生成成功率 ≥ 99.5%
- 分享→注册→首单链路数据完备率 ≥ 99%
- 奖励发放 SLA ≤ 5 分钟（触发后到成功入账）
- 违规分享检测误报率 ≤ 1%

## 3. 详细需求

### 3.1 REQ-social-features-001 分享链接生成与管理

- **业务描述**: 用户针对商品、活动、专题等资源生成可追踪的唯一分享代码，系统返回短链、二维码、有效期信息，并允许用户或运营停用、刷新。
- **用户故事**: 作为注册用户，我希望一键生成针对商品的分享链接并在社群传播，以便获取邀请奖励。
- **业务规则**:
  1. 仅支持在资源允许分享、库存正常的情况下生成链接
  2. 默认有效期 30 天，可在运营规则内缩短但不可延长超过 90 天
  3. 同一资源同一用户在 24 小时内最多生成 5 条有效链接，超限提示复用
- **依赖**: `product_catalog`/`marketing_campaigns` 校验资源有效性；`user_auth` 提供身份信息
- **验收标准**:
  - [ ] 支持商品、活动两类资源类型，接口返回 share_code、share_url、qr_code_url
  - [ ] 记录渠道（wechat, moments, copy_link 等）并可更新
  - [ ] 支持停用/启用操作，停用后事件写入 audit log
  - [ ] 链接生成接口响应时间 ≤ 300ms（95 百分位）

### 3.2 REQ-social-features-002 分享与转化事件采集

- **业务描述**: 收集分享点击、邀请注册、首单完成等关键节点，形成可串联的转化链路，支撑奖励发放与运营分析。
- **用户故事**: 作为运营，我希望清楚看到每一条分享链接的点击、注册、首单人数，以评估活动效果。
- **业务规则**:
  1. 分享点击记录需包含 share_code、渠道、client_ip、user_agent、session_id
  2. 注册、首单等事件需与用户、订单 ID 关联并落地到 `social_share_events`
  3. 同一 session 在 5 分钟内重复点击仅计一次有效点击
- **依赖**: `user_auth` 注册事件、`order_management` 首单事件（事件总线）
- **验收标准**:
  - [ ] 提供匿名点击上报接口，数据入库并支持幂等
  - [ ] 支持消费注册、首单事件并回写事件表
  - [ ] 提供查询接口返回点击、注册、首单指标
  - [ ] 数据落地时间戳精度毫秒级，保留原始 UA/IP 便于风控

### 3.3 REQ-social-features-003 邀请关系与奖励判定

- **业务描述**: 根据分享事件生成 inviter-invitee 关系，判断被邀请人是否满足奖励条件（如完成注册+首单），形成奖励任务。
- **用户故事**: 作为邀请人，我希望系统能正确识别我邀请的好友，并在好友下单后提示奖励状态。
- **业务规则**:
  1. 使用最先触发的 share_code 建立关系，防止多方竞争
  2. 首单判定需考虑订单取消、退款等状态
  3. 同一被邀请人只能关联一个邀请人，若之前存在关系则不再变更
- **依赖**: `order_management` 订单状态事件、`member_system` 用户身份信息
- **验收标准**:
  - [ ] `social_referrals` 表记录 inviter_user_id、invitee_user_id、status、first_order_id
  - [ ] 支持订单回退场景的状态回滚（首单退款后状态回到 registered）
  - [ ] 奖励判定规则可按活动配置（积分奖励、优惠券奖励）
  - [ ] 状态流转记录审计日志

### 3.4 REQ-social-features-004 奖励履约协调

- **业务描述**: 当邀请关系满足条件后，模块生成奖励任务并调用对应模块发放积分或优惠券，跟踪成功/失败并支持重试。
- **用户故事**: 作为邀请成功的用户，我希望奖励能够及时发放，并能看到奖励状态。
- **业务规则**:
  1. 奖励类型支持积分、优惠券、余额等，依据活动配置
  2. 调用外部模块失败需重试 3 次，仍失败时进入人工处理队列
  3. 奖励重复发放需防重，确保 reward_code 唯一
- **依赖**: `member_system` 积分发放 API、`marketing_campaigns` 优惠券发放 API、`notification_service`（发送通知）
- **验收标准**:
  - [ ] `social_rewards` 表记录 reward_type、value、status、external_reference
  - [ ] 奖励发放采用幂等键（invitee_user_id + activity_id）
  - [ ] 提供查询接口返回用户奖励历史及状态
  - [ ] 失败重试策略可配置，默认 5 分钟间隔、3 次

### 3.5 REQ-social-features-005 违规检测与限流

- **业务描述**: 识别并限制恶意分享、刷奖励、异常 IP 集中等行为，保障活动公平性。
- **用户故事**: 作为运营，我希望系统阻止异常账号通过脚本刷奖励，减少损失。
- **业务规则**:
  1. 单个用户每日有效邀请数可在活动中配置（默认 20 人）
  2. 同一 IP 在 10 分钟内的有效点击上限默认 30 次，超过则暂时屏蔽
  3. 黑名单（用户/设备/IP）由运营维护，模块需实时引用
- **依赖**: Redis 计数器、风控黑名单（待由 risk_control_system 提供）
- **验收标准**:
  - [ ] 接口支持阈值配置并持久化
  - [ ] 命中限制时返回明确错误码（如 `SOCIAL_429`）并记录审计日志
  - [ ] 违规名单可通过 API 导出/查询

### 3.6 REQ-social-features-006 运营指标与导出

- **业务描述**: 为运营提供渠道对比、邀请漏斗、奖励发放等指标查询，以及 CSV 导出能力。
- **用户故事**: 作为运营，我希望按日期、渠道查看分享数量、注册数、首单数、奖励成本，以评估活动 ROI。
- **业务规则**:
  1. 指标支持按日期、渠道、活动筛选
  2. 导出文件需在 1 分钟内生成，超过阈值执行异步任务并邮件通知
  3. 指标数据与原始事件保持一致性，每日 02:00 生成快照表
- **依赖**: 数据仓库/BI（可选），`social_share_daily_stats` 快照表
- **验收标准**:
  - [ ] 提供 `/admin/metrics/daily` 接口返回关键指标
  - [ ] 支持 CSV 导出与异步任务模式
  - [ ] 与运营提供的校验样本对齐误差 < 1%

## 4. 非功能需求

- **性能**: 遵循性能标准中社交模块指标——接口响应 < 500ms、分享统计刷新 < 300ms
- **可用性**: 99.9% 可用性，模块异常时不影响核心交易，可降级为提示“分享功能暂不可用”
- **安全**: 所有接口需 JWT 鉴权（匿名统计接口除外）；记录 security_logger 安全日志；遵循 `docs/standards/api-standards.md`
- **合规**: 保存分享人、被邀请人授权信息，满足《广告法》《反不正当竞争法》宣传要求

## 5. 依赖与约束

- **系统依赖**:
  - `user_auth`: JWT、用户基本信息
  - `product_catalog`、`marketing_campaigns`: 资源合法性校验、活动配置
  - `order_management`: 首单事件、退款事件
  - `member_system`、`marketing_campaigns`: 奖励发放
  - `notification_service`: 奖励结果通知（订阅事件）
- **技术约束**:
  - 使用 MySQL 8.0，遵循统一主键与索引标准
  - 事件通信遵循项目事件总线约定，消息格式需与 `docs/architecture/integration.md` 对齐
- **时间规划**:
  - M1（2025-11-07）完成分享生成与事件采集
  - M2（2025-11-21）完成奖励判定与履约协调
  - M3（2025-12-05）上线运营指标、风控限流能力

## 6. 风险与应对

| 风险 | 描述 | 影响 | 缓解措施 |
|------|------|------|----------|
| 数据缺口 | 注册/订单事件未及时到达 | 奖励延迟或丢失 | 引入补偿任务，定期对账订单数据 |
| 外部发放失败 | 积分/优惠券接口故障 | 奖励无法履约 | 设计重试+人工处理队列，通知运营 |
| 滥用风险 | 脚本批量刷邀请 | 成本失控 | 限流、黑名单、异常模式检测 |
| 法规风险 | 活动宣传不合规 | 监管处罚 | 需运营提供素材审核、记录用户同意 |
