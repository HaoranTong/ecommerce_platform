# Payment Service 模块边界分析

**分析日期**: 2025-10-20  
**模块版本**: v1.0.0 (设计阶段)  
**分析人**: GitHub Copilot  

## 业务域归属
- **所属业务域**: 交易域 (Transaction Domain)
- **领域定位**: 核心 (Core)
- **业务价值**: 支付结算是电商交易闭环的关键环节，直接影响用户体验和资金安全

## 边界定义（来自 business-architecture.md）

### 包含功能（必须实现）

根据 `docs/architecture/business-architecture.md` 和 `docs/requirements/functional.md`，支付服务模块的核心职责包括：

1. ✅ **支付处理** - 处理订单支付请求，支持多种支付方式
   - 7种支付方式：微信支付、支付宝、银行卡、企业转账、余额支付、积分支付、组合支付
   - 支付请求创建和验证
   - 支付状态跟踪和更新
   - 支付超时处理

2. ✅ **退款管理** - 处理订单退款请求
   - 全额退款和部分退款
   - 退款审核流程
   - 退款状态跟踪
   - 退款到账通知

3. ✅ **支付适配器模式** - 统一的支付接口，隔离第三方支付细节
   - 微信支付适配器
   - 支付宝支付适配器
   - 银行卡支付适配器
   - 其他支付渠道适配器

4. ✅ **支付安全保障** - 支付风险防控和资金安全保护
   - 支付金额校验
   - 重复支付检测
   - 支付token验证
   - 支付密码验证（如需要）

5. ✅ **对账结算** - 资金流水和结算记录管理
   - 支付流水记录
   - 结算对账
   - 财务报表数据

6. ✅ **企业支付服务** - B2B企业客户支付支持
   - 对公转账
   - 月结账期
   - 发票管理关联

7. ✅ **移动支付优化** - 微信生态深度集成
   - 微信小程序支付
   - 微信公众号支付
   - 移动端优化体验

### 排除功能（明确由其他模块负责）

1. ❌ **订单创建和管理** → `order_management` 模块
   - 理由：订单状态和生命周期管理是订单模块的职责
   - 边界：支付模块只接收订单ID和支付金额，不参与订单创建

2. ❌ **库存扣减** → `inventory_management` 模块
   - 理由：库存管理和预占释放属于库存模块职责
   - 边界：支付成功后通过事件通知库存模块，不直接操作库存

3. ❌ **优惠券核销** → `marketing_campaigns` 模块
   - 理由：营销优惠逻辑属于营销模块
   - 边界：支付模块接收折后金额，不参与优惠计算

4. ❌ **会员积分变动** → `member_system` 模块
   - 理由：会员权益和积分规则属于会员模块
   - 边界：支付成功后通过事件通知会员模块，不直接操作积分

5. ❌ **物流配送** → `logistics_management` 模块
   - 理由：配送流程属于物流模块职责
   - 边界：支付成功后通过事件触发发货流程

6. ❌ **消息通知** → `notification_service` 模块
   - 理由：消息推送属于通知服务模块
   - 边界：支付模块记录支付结果，由通知模块负责消息发送

7. ❌ **风险评估和反欺诈** → `risk_control_system` 模块
   - 理由：风控规则和策略属于风控模块
   - 边界：支付模块调用风控接口进行风险检查，不实现风控逻辑

8. ❌ **用户认证和授权** → `user_auth` 模块
   - 理由：用户身份验证属于用户认证模块
   - 边界：支付模块依赖JWT token，不参与用户认证

## 依赖关系

### 依赖模块（我需要调用的模块）

根据 `docs/architecture/application-architecture.md` 和业务流程分析：

1. **user_auth** - 用户身份验证
   - 依赖原因：需要验证用户身份和支付权限
   - 调用场景：支付请求时验证用户token

2. **order_management** - 订单信息查询
   - 依赖原因：需要验证订单状态和金额
   - 调用场景：支付前验证订单有效性，支付成功后更新订单状态

3. **risk_control_system** (可选，第三期) - 风险控制
   - 依赖原因：支付前需要进行风险评估
   - 调用场景：大额支付、异常支付检测

### 被依赖模块（谁调用我）

1. **order_management** - 订单支付场景
   - 被依赖场景：用户下单后发起支付
   - 接口：创建支付请求、查询支付状态

2. **member_system** (第二期) - 会员充值场景
   - 被依赖场景：会员余额充值
   - 接口：创建充值支付请求

3. **distributor_management** (第三期) - 分销商提现场景
   - 被依赖场景：分销商佣金提现
   - 接口：创建提现转账请求

## 核心实体

基于 business-architecture.md 定义：

1. **Payment** (支付记录)
   - 职责：记录支付请求、状态、结果
   - 关键属性：支付单号、订单ID、用户ID、支付金额、支付方式、支付状态、第三方流水号

2. **Refund** (退款记录)
   - 职责：记录退款请求、审核、结果
   - 关键属性：退款单号、支付ID、订单ID、退款金额、退款原因、退款状态、审核状态

3. **PaymentTransaction** (支付流水)
   - 职责：记录所有资金变动明细
   - 关键属性：流水号、交易类型、金额、时间、关联支付/退款ID

4. **PaymentMethod** (支付方式配置)
   - 职责：管理可用的支付渠道和配置
   - 关键属性：支付方式代码、名称、是否启用、排序、配置参数

## 主要业务规则

1. **支付金额一致性**
   - 支付请求金额必须与订单金额一致
   - 退款金额不得超过已支付金额

2. **支付幂等性**
   - 相同订单的重复支付请求应返回已有支付结果
   - 支付流水号全局唯一

3. **支付状态机**
   - PENDING(待支付) → PROCESSING(处理中) → SUCCESS(成功) / FAILED(失败) / TIMEOUT(超时)
   - 状态流转不可逆（除超时可重试）

4. **退款状态机**
   - PENDING(待审核) → APPROVED(已批准) → PROCESSING(处理中) → SUCCESS(成功) / FAILED(失败)

5. **支付超时处理**
   - 支付请求创建后30分钟未完成自动超时
   - 超时订单释放库存预占

6. **支付安全规则**
   - 大额支付（>5000元）需要额外验证
   - 连续失败3次锁定支付功能30分钟
   - 敏感支付需要支付密码验证

## 潜在边界冲突点识别

### 1. 支付成功后的后续操作

**冲突点**: 支付成功后需要触发多个模块的操作（订单状态更新、库存扣减、积分增加等）

**解决方案**:
- 采用事件驱动架构
- 支付模块发布 `PaymentSuccessEvent` 事件
- 其他模块订阅事件并执行各自的业务逻辑
- 支付模块不直接调用其他模块的状态更新接口

### 2. 优惠金额的处理

**冲突点**: 支付金额可能包含优惠券、积分抵扣等营销活动影响

**解决方案**:
- 支付模块只接收最终应付金额
- 优惠计算由 order_management 模块协调 marketing_campaigns 完成
- 支付模块不参与优惠规则计算，只负责收款

### 3. 退款审核流程

**冲突点**: 退款审核可能涉及客服、风控等多个角色

**解决方案**:
- 支付模块提供退款审核接口
- 审核权限由 user_auth 模块管理
- 风险评估调用 risk_control_system 接口
- 支付模块只负责退款执行

### 4. 第三方支付回调处理

**冲突点**: 第三方支付异步回调需要更新多个系统状态

**解决方案**:
- 支付模块接收并验证回调
- 更新支付状态后发布事件
- 保证回调幂等性处理
- 失败重试机制

## 架构约束

1. **适配器模式强制**
   - 所有第三方支付必须通过适配器封装
   - 核心业务逻辑不依赖具体支付渠道

2. **事务边界控制**
   - 支付状态更新必须在数据库事务中
   - 跨模块操作通过事件异步处理

3. **幂等性保证**
   - 所有支付接口必须支持幂等调用
   - 使用唯一支付单号防重

4. **安全性优先**
   - 敏感数据加密存储
   - 支付密码单向加密
   - 支付token有效期控制
